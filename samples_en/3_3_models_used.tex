\section{Models Used}

Two code-specific large language models are selected for the experiments:
\texttt{bigcode/starcoder2-3b} and
\texttt{Qwen/Qwen2.5-Coder-3B-Instruct}. Both models are relatively lightweight
compared to larger code-focused models, making them suitable for training and
evaluation under limited hardware resources, while still providing strong coding
capabilities. Table~\ref{tab:model_overview} provides an overview of the evaluated models,
including their size, context length, training data scale, and fine-tuning setup.

For each model, two variants are evaluated. The first variant uses the publicly
available checkpoint released by the model provider, without additional
Java-to-C++ fine-tuning performed in this thesis. In the case of
\texttt{Qwen/Qwen2.5-Coder-3B-Instruct}, this checkpoint is already
instruction-tuned for coding tasks, but it is not specifically fine-tuned here
for the Java-to-C++ translation task. The second variant is the same model after
additional task-specific fine-tuning on Java-to-C++ examples.

The \texttt{bigcode/starcoder2-3b} model is a decoder-only Transformer model
with approximately 3 billion parameters. It is part of the StarCoder2 family
and is trained on more than 3 trillion tokens collected from large-scale code
repositories and software-related text sources. The model supports 17
programming languages and provides a context window of up to 16,384 tokens
\cite{starcoder2, starcoder2_hf}. At the time of its release, StarCoder2-3B
outperformed several other code models of similar size on standard programming benchmarks.

The \texttt{Qwen/Qwen2.5-Coder-3B-Instruct} model is also a decoder-only
Transformer model with approximately 3.09 billion parameters. Unlike
StarCoder2, it is instruction-tuned for coding tasks, which makes it more
suitable for prompt-based code generation and translation. The model supports a
context length of up to 32,768 tokens and is trained on more than 5.5 trillion
tokens \cite{qwen_coder, qwen_coder_report}. Qwen2.5-Coder models are optimized
for programming-related tasks such as code generation, reasoning, debugging,
and repair.

In addition to the original pre-trained models, fine-tuned variants of both
\texttt{bigcode/starcoder2-3b} and \texttt{Qwen/Qwen2.5-Coder-3B-Instruct} are
prepared for the Java-to-C++ translation task. Fine-tuning is performed using
Low-Rank Adaptation (LoRA) \cite{hu2021lora, lora_modules, qwen_lora},
which adds small trainable matrices to selected
layers of the model while keeping the original weights frozen
\cite{hu2021lora}. This significantly reduces the number of trainable parameters
and makes fine-tuning more efficient.

Both models are fine-tuned using 4-bit quantization together with LoRA, which
corresponds to the QLoRA approach \cite{qwen_lora_repo, qwen_lora, dettmers2023qlora}. In this setup, the original model weights
remain frozen and quantized, while only the LoRA adapter weights are updated
during training. This reduces GPU memory usage and makes it possible to
fine-tune billion-parameter models under limited hardware resources. Mixed
precision and gradient checkpointing are also used to further reduce memory
requirements.


The same LoRA configuration is used for both models. The low-rank dimension
is set to $r = 8$, the LoRA scaling factor to $\alpha = 16$, and the dropout
rate to 0.05. The adapters are applied to both the attention and feed-forward
layers of the models, specifically to the
\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj},
\texttt{o\_proj}, \texttt{gate\_proj}, \texttt{up\_proj}, and
\texttt{down\_proj} modules. Applying LoRA to both attention and feed-forward
layers is a common approach because it provides stronger adaptation than using
attention layers alone \cite{lora_modules, hu2021lora}.

The maximum sequence length during training is set to 1024 tokens. Both models
are trained for two epochs using a learning rate of $10^{-4}$, cosine learning
rate scheduling, a warmup ratio of 0.03, and gradient accumulation with 16
steps. The effective batch size per device is 1. These settings are selected
to balance training stability and GPU memory consumption.
