\chapter{Methodology}

This chapter describes the methodology used to evaluate deep learning-based code translation models. The study focuses
on comparing models under a unified experimental setup, using both
similarity-based and execution-based evaluation techniques.

Code translation outputs are evaluated using both similarity-based and
execution-based approaches. Specifically, BLEU \cite{bleu_metric} score is used as a
similarity-based metric, while functional correctness is assessed through
execution-based evaluation using the CodeEditorBench \cite{codeeditorbench} framework, which measures
model performance on practical coding tasks such as translation and debugging,
providing a more realistic estimate of actual program behavior.

The following sections detail the experimental setup, including the evaluated
code-oriented language models (in both base and fine-tuned variants), the
training dataset used for fine-tuning, the code translation pipeline, and the
evaluation procedure.

\section{Experimental Setup}

The experiments are designed to compare the performance of base and fine-tuned
code translation models under identical conditions. Two open-source
code-specific large language models are selected for evaluation: the
\texttt{bigcode/starcoder2-3b} model \cite{starcoder2} and the
\texttt{Qwen/Qwen2.5-Coder-3B-Instruct} model \cite{qwen_coder}.

For both models, two experimental variants are prepared. The first
variant uses the original model without any additional task-specific
fine-tuning for code translation. The second variant uses a
fine-tuned version of the same model, trained specifically for Java-to-C++ code
translation. This setup enables a direct comparison between models without task-specific adaptation and
models adapted through fine-tuning, making it possible to analyze the impact
of task-specific training on translation quality.

The experiments focus exclusively on Java-to-C++ translation. This direction is
selected because Java and C++ are both widely used yet substantially different
programming languages in terms of execution model, abstraction level, and memory
management. Java relies on automatic garbage collection and execution through
the Java Virtual Machine, whereas C++ provides lower-level control and typically
requires manual memory management, leading to fundamental differences in program
structure and behavior. These differences make
Java-to-C++ translation more challenging than translation between more closely
related languages. In addition, the XLCoST dataset contains a substantial number
of aligned Java and C++ code pairs, and the CodeEditorBench framework supports
this language pair, enabling consistent training and evaluation across all
models.

The experimental workflow consists of two main phases. In the first phase, the
base models are evaluated directly on the Java-to-C++ translation task in order
to measure their original performance without additional task-specific
adaptation. For each Java input sample, the model generates a C++ translation.
The generated output is then compared against the reference
\texttt{target\_code} provided in the CodeEditorBench dataset in order to
compute BLEU score. The same generated translation is also compiled and
executed inside the CodeEditorBench environment to assess functional
correctness.

In the second phase, the same models are fine-tuned for Java-to-C++ code
translation and evaluated again using the identical procedure. This makes it
possible to directly compare the performance of the base and fine-tuned
variants.

The XLCoST dataset is used as the primary training resource for the fine-tuned models. XLCoST
contains aligned code snippets across multiple programming languages, including
Java and C++, making it suitable for supervised code translation tasks. The
Java--C++ pairs are first extracted and transformed into instruction-based
prompts, then tokenized and prepared for training. Fine-tuning is performed
using parameter-efficient methods in order to reduce hardware requirements and
training time while still allowing the models to adapt to the translation task.

As mentioned above, one of the two models selected for the experiments is the
StarCoder2-3B model \cite{starcoder2, starcoder2_hf}, which is chosen for its
strong coding capabilities despite its relatively small size. StarCoder2 models
are trained on large-scale code corpora containing trillions of tokens and have
been shown to outperform several models of similar size on code-related tasks.
The second selected model is Qwen2.5-Coder-3B-Instruct, which is specifically
optimized for programming tasks and demonstrates strong performance on code
generation and repair benchmarks \cite{qwen_coder, qwen_coder_report}. The
Qwen2.5-Coder series is trained on a large-scale corpus of over 5.5 trillion
tokens, enabling competitive performance across a wide range of coding tasks.

Execution-based evaluation is performed using the CodeEditorBench framework.
CodeEditorBench evaluates model outputs in realistic coding scenarios,
including translation tasks, by compiling and running generated code against
predefined test cases. The evaluation environment is
executed inside a Docker container using the official CodeEditorBench image.
Using Docker ensures that all experiments are performed in an isolated and
reproducible environment, reducing the risk of issues caused by missing
dependencies, compiler version differences, or operating system variations.
Container-based execution also provides sandboxing, which is important when
running automatically generated code because it limits the potential impact of
compilation failures, runtime errors, or unintended system-level behavior.

To ensure fair comparison, all models are evaluated on the same Java-to-C++
pairs of CodeEditorBench and use a consistent instruction structure, while adapting the prompt format to match the expected input template of each model,
preprocessing pipeline, and generation settings. Each input example is converted into an instruction-following prompt consisting of a system message, a user request, and the original Java code.

The prompt formatting differs slightly depending on the model. For
the StarCoder2 model, a plain text instruction format is used. In contrast, the
Qwen2.5-Coder-Instruct model requires a structured ChatML-based format, where
special tokens explicitly separate system, user, and assistant roles. This structure reflects the format used during instruction tuning of the model and ensures alignment between training and inference inputs.

The ChatML-based prompt format used for Qwen2.5-Coder-Instruct is shown below:

\begin{lstlisting}
<|im_start|>system
You are an expert code translator. Translate Java code to C++ preserving logic and I/O.
<|im_end|>
<|im_start|>user
Translate this Java code to C++.

<source code>
<|im_end|>
<|im_start|>assistant
\end{lstlisting}

For comparison purposes, a simpler instruction-style format is used for the
StarCoder2 model:

\begin{lstlisting}
### System
You are an expert code translator. Translate Java code to C++ preserving logic and I/O.

### User
Translate this Java code to C++.

### Java
<source code>

Answer (C++)
\end{lstlisting}

Only the generated C++ output corresponding to the assistant response is used
as the training target. For the StarCoder2 model, this corresponds to the code
following the \texttt{\#\#\# Answer (C++)} tag, while for the
Qwen2.5-Coder-Instruct model, it corresponds to the tokens generated after the
assistant role marker in the ChatML format. In both cases, all preceding prompt
tokens are masked using \texttt{-100} labels so that the loss is computed only
on the translated C++ output.

The same tokenizer settings, truncation strategy, and maximum sequence length
of 1024 tokens are used for all models. During inference, generation is
performed with a maximum of 900 new tokens, a repetition penalty of 1.10,
\texttt{top\_p=0.95}, and \texttt{temperature=0.2}. Greedy decoding is used
to ensure deterministic outputs across repeated runs.

After generation, all outputs are postprocessed using the same cleaning
pipeline. This step removes markdown code fences, duplicated prompt fragments,
incomplete trailing sections, and any repeated system or user messages. BLEU
score is then computed against the reference C++ translation, while
execution-based evaluation is performed by compiling and running the generated
code inside the Docker-based CodeEditorBench environment.
